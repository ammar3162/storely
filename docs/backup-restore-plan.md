# خطة النسخ الاحتياطي والاسترجاع — ستورلي

آخر تحديث: 2026-11-17 · المالك: صاحب ستورلي · المراجعة: كل 3 أشهر

**نقاط الضعف**
1. كل النسخ عند نفس المزود ونفس المشروع: لو انحذف المشروع أو اختُرق أو تعطّل الحساب، تضيع النسخ مع الأصل.
2. أقصى خسارة بيانات ممكنة اليوم = 24 ساعة (لا يوجد PITR).
3. لا يوجد تنبيه لو فشل النسخ.
4. لا يوجد إجراء استرجاع مكتوب، ولم يُجرَّب استرجاع فعلي قط.

## 2. الأهداف

- **أقصى خسارة بيانات (RPO):** 24 ساعة الآن ← ساعة واحدة عند تفعيل PITR لاحقاً (عند ~50 عميل مدفوع).
- **أقصى وقت توقف (RTO):** 4 ساعات للاسترجاع الكامل في مشروع جديد، و30 دقيقة لاسترجاع بيانات منشأة واحدة.
- **قاعدة 3-2-1:** 3 نسخ، على وسيطين مختلفين، واحدة منها خارج Supabase.

## 3. الخطة

### المرحلة 1 — نسخة خارجية يومية مشفّرة (الأهم)
- **الوجهة المقترحة:** Cloudflare R2 (أول 10 جيجا مجاناً، بدون رسوم سحب). البديل: Amazon S3 عند تفعيل حساب AWS.
- **التشغيل:** GitHub Actions كل ليلة 01:00 بتوقيت السعودية:
  1. `pg_dump` لقاعدة الإنتاج كاملة (حوالي 10–15 ميجا مضغوطة).
  2. تشفير بمفتاح `age` العام (المفتاح الخاص عند المالك فقط، في مدير كلمات المرور — لا يُرفع لأي مكان).
  3. رفع إلى R2: `db/daily/YYYY-MM-DD.sql.gz.age`.
- **الاحتفاظ:** اليومي 30 يوماً، ونسخة أول كل شهر 12 شهراً (قاعدة دورة حياة في R2).
- **صور الفواتير والشعارات (~3 جيجا):** مزامنة أسبوعية بـ `rclone` إلى `storage/` في نفس الحاوية.
- **الأسرار (يضعها المالك بنفسه في GitHub → Settings → Secrets):** رابط اتصال قاعدة الإنتاج (مستخدم قراءة فقط)، مفاتيح R2. لا تُكتب في الكود ولا تُرسل في المحادثات.

### المرحلة 2 — التنبيه
- فشل مهمة GitHub يرسل إيميلاً تلقائياً لصاحب المستودع.
- فحص الصحة (كل ساعة) يضيف: تنبيه واتساب للإدارة لو آخر نسخة خارجية أقدم من 26 ساعة، أو آخر تصدير CSV أقدم من 8 أيام، أو صور غير منسوخة لأكثر من يومين.

### المرحلة 3 — تمرين استرجاع كل 3 أشهر
1. فك تشفير آخر نسخة يومية واسترجاعها في مشروع Supabase مؤقت (أو قاعدة محلية).
2. مقارنة عدد الصفوف في الجداول الرئيسية مع الإنتاج.
3. تسجيل النتيجة والوقت المستغرق في هذا الملف (قسم 6).

### المرحلة 4 — لاحقاً
- تفعيل PITR في Supabase (حوالي 100 دولار شهرياً) عند ~50 عميل مدفوع.
- توسيع تصدير CSV الأسبوعي ليشمل الإقفال والموظفين والحضور والرواتب والموردين (مفيد للعميل نفسه).

## 4. إجراءات الاسترجاع

### أ) استرجاع بيانات منشأة واحدة (حذف بالخطأ)
1. تحديد الوقت والجداول المتأثرة.
2. فك تشفير آخر نسخة قبل الحذف واسترجاعها في قاعدة مؤقتة.
3. استخراج صفوف `org_id` المطلوبة فقط وإدخالها في الإنتاج عبر ملف SQL موثّق في `supabase/security-fixes/` مع ملف تراجع.
4. حركة المخزون: الكمية تُحسب من `stock_movements` (لا تُكتب `qty` مباشرة).

### ب) عطل كامل في قاعدة الإنتاج (المشروع موجود)
1. تفعيل وضع الصيانة من لوحة الإدارة.
2. Supabase Dashboard → Database → Backups → Restore لآخر نسخة يومية (يستبدل القاعدة كاملة — كل ما بعد النسخة يضيع).
3. التحقق: فحص الصحة، تسجيل دخول تجريبي، عدد المنشآت.
4. إلغاء وضع الصيانة وإبلاغ العملاء بما فُقد إن وُجد.

### ج) فقدان المشروع أو الحساب
1. إنشاء مشروع Supabase جديد في نفس المنطقة (ap-southeast-2).
2. فك تشفير آخر نسخة خارجية و`psql`/`pg_restore` فيها.
3. إعادة مزامنة الملفات من R2 إلى مجلدات التخزين، وضبط خصوصية المجلدات كما كانت.
4. تحديث متغيرات Supabase (الرابط والمفاتيح) في **مشروعي Vercel** وإعادة النشر.
5. إعادة ربط روابط Auth (Site URL، Redirect URLs) وقوالب الإيميل.

## 5. مسؤوليات
- **المالك:** إنشاء حساب الوجهة (R2)، وضع الأسرار، الاحتفاظ بمفتاح التشفير الخاص، اعتماد أي استرجاع في الإنتاج.
- **التطوير:** كتابة مهام النسخ والتنبيه، تحديث هذا الملف، تنفيذ تمرين الاسترجاع.
